useState local state
useState
Adds reactive local state to a function component. Returns a value and a setter — calling the setter triggers a re-render with the new value.
const [count, setCount] = useState(0)
useEffect side effects
useEffect
Runs a side-effect after render. Use for data fetching, subscriptions, or DOM mutations. The dependency array controls when it re-runs.
useEffect(() => fetchData(), [id])
useContext global ctx
useContext
Reads and subscribes to a React context. Avoids prop-drilling by making shared values (theme, auth, locale) accessible anywhere in the tree.
const theme = useContext(ThemeCtx)
useRef DOM access
useRef
Returns a mutable ref object whose .current persists across renders without causing re-renders. Ideal for direct DOM access or storing instance values.
const el = useRef(null)
useMemo memoized val
useMemo
Caches the result of an expensive calculation between renders. Only recomputes when its dependencies change — prevents redundant heavy work.
const sorted = useMemo(() => sort(list), [list])
useCallback stable fn
useCallback
Returns a memoized version of a callback that only changes when dependencies change. Prevents child re-renders caused by new function references.
const fn = useCallback(() => doX(), [x])

Event Loop — Call Stack, Microtasks & Task Queue
The most important concept in JavaScript runtime — watch how sync code, Promises (microtasks), and setTimeout (macrotasks) are scheduled and executed.
JavaScript Runtime
Call Stack
LIFO structure. Synchronous functions pushed and popped. Blocks the main thread while executing.
Microtask Queue
Promise callbacks (.then, .catch). Processed after every task, before the next macrotask. Higher priority.
Task Queue
setTimeout, setInterval, I/O events. Processed one at a time when the call stack is empty.

Core Web Vitals

📊
Core Web Vitals — The Three Pillars
Google's three Core Web Vitals measure Loading, Interactivity, and Visual Stability. They directly impact Search ranking and user satisfaction.
Core Web Vitals
🖼 LCP
Largest Contentful Paint
Time until the largest image or text block is visible. Good: <2.5s · Needs work: 2.5–4s · Poor: >4s
✅ <2.5s⚠ 2.5–4s❌ >4s
👆 INP
Interaction to Next Paint
Latency of all user interactions (click, tap, keypress). Replaced FID in 2024. Good: <200ms
✅ <200ms⚠ 200–500ms❌ >500ms
📐 CLS
Cumulative Layout Shift
Unexpected layout shifts while loading. Set size on images/embeds to prevent. Good: <0.1
✅ <0.1⚠ 0.1–0.25❌ >0.25
⚡
Supporting Metrics — TTFB, FCP, TBT
Beyond the three Core Vitals, these diagnostic metrics pinpoint bottlenecks in the loading pipeline.
Loading Timeline
🚀 TTFB
Time To First Byte — server response speed. Good: <800ms. Reduce with CDN, caching, edge functions.
🎨 FCP
First Contentful Paint — first text or image. Good: <1.8s. Eliminate render-blocking resources.
🧱 TBT
Total Blocking Time — JS tasks blocking main thread. Good: <200ms. Split long tasks, use Web Workers.
⏱ TTI
Time To Interactive — fully responsive. Good: <3.8s. Defer non-critical JS, minimize main-thread work.

🔒 Security

Frontend Security

Protect your application from XSS, CSRF, clickjacking and injection attacks — with automated scanning, security headers and defence-in-depth strategies.

🛡️
Security Threat Landscape
Animated overview of the most critical frontend attack vectors and how each is mitigated.
Security Threats
⚠️
XSS — Cross-Site Scripting
XSS allows attackers to inject malicious scripts into pages viewed by other users. Three variants: Stored, Reflected, and DOM-based.
💾 Stored XSS
Malicious script saved to the database. Every user who loads the page executes it. Highest severity.
🔗 Reflected XSS
Script embedded in URL, reflected back in server response. Requires victim to click a crafted link.
🖥 DOM-Based XSS
Client-side script reads from an attacker-controlled source (URL hash) and writes to a dangerous sink (innerHTML).
Prevention Techniques
// ❌ Dangerous — never do this
el.innerHTML = userInput;
document.write(data);

// ✅ Safe alternatives
el.textContent = userInput; // text only
el.setAttribute('data-x', sanitized);
import DOMPurify from 'dompurify';
el.innerHTML = DOMPurify.sanitize(html);
Content Security Policy (CSP)
HTTP header whitelist of trusted script sources. Blocks inline scripts and unauthorized origins.
Content-Security-Policy: script-src 'self' cdn.example.com
HttpOnly & Secure Cookies
Prevents JS from accessing session cookies. Always set HttpOnly, Secure, and SameSite=Strict on auth cookies.
🔄
CORS & CSRF Protection
CORS controls which origins can access your API. CSRF exploits the browser's automatic cookie sending to forge authenticated requests.
🌐 CORS (Cross-Origin Resource Sharing)
Browser enforces the Same-Origin Policy. CORS headers tell the browser which cross-origin requests are allowed. A preflight OPTIONS request checks permissions before the real request.
// Express CORS setup
app.use(cors({
  origin: ['https://app.example.com'],
  methods: ['GET','POST'],
  credentials: true,
}));
🔄 CSRF (Cross-Site Request Forgery)
Attacker tricks authenticated user into making an unintended request. Mitigated with CSRF tokens, SameSite cookies, and double-submit cookie pattern.
// SameSite cookie — blocks CSRF
res.cookie('session', token, {
  httpOnly: true,
  secure: true,
  sameSite: 'Strict',
});

Frontend Testing Strategy

From smoke tests to full regression suites — understand testing types, the testing pyramid, and how to build a strategy that catches bugs without slowing down development.

🔺
The Testing Pyramid & Strategy
The testing pyramid defines the ideal ratio of unit, integration, and E2E tests — more fast cheap unit tests at the base, fewer slow expensive E2E at the top.
Testing Pyramid
🧪
Test Types — Smoke, Functional & More
Each testing type serves a different role in the quality pipeline — from fast sanity checks to detailed behavioural verification.
💨 Smoke Testing
A quick sanity check — verify that the most critical user paths work after a new build or deployment. If smoke tests fail, deeper testing is skipped entirely.
What to smoke test:
▸ App loads without crash
▸ Login / signup flow works
▸ Core navigation routes respond
▸ API health endpoints return 200
▸ Payment / checkout flow accessible
✅ Functional Testing
Verifies that each feature behaves according to its specification — inputs produce expected outputs, UI interactions trigger correct state changes and API calls.
Tools & Techniques:
▸ Jest + React Testing Library (component)
▸ Cypress / Playwright (browser automation)
▸ Given-When-Then BDD pattern
▸ Mock APIs with MSW (Mock Service Worker)
▸ Accessibility testing with axe-core
🔗 Integration Testing
Tests how multiple units work together — component + API + state. Catches bugs at the boundaries that unit tests miss.
// React Testing Library
render(<UserProfile userId="1" />);
await waitFor(()=>
  expect(screen.getByText('Alice')).toBeInTheDocument()

Node.js — Non-blocking I/O Runtime
V8-powered JavaScript runtime built on an event-driven, non-blocking I/O model — ideal for I/O-heavy, real-time and API-heavy workloads.
Node.js Event Loop
🔄 Event Loop Phases
1 · timers (setTimeout/setInterval)
2 · pending callbacks
3 · idle, prepare
4 · poll (I/O events wait here)
5 · check (setImmediate)
6 · close callbacks
⚡ libuv Thread Pool

Node's event loop runs on a single thread, but libuv uses a thread pool (default 4 threads) for blocking operations: DNS lookups, file system I/O, crypto, and zlib. Network I/O uses OS async APIs (epoll/kqueue) — no thread needed.

UV_THREADPOOL_SIZEmax 128 threads
📦 Module System

CommonJS (CJS): synchronous require(), module.exports. Default in Node. ESM: static import/export, tree-shakeable. Use .mjs or "type":"module" in package.json. Cannot mix without wrappers.

ESMCJSWorker Threads
🌊
Streams, Buffers & Worker Threads
Process large data without loading it fully into memory. Streams are the backbone of HTTP, file I/O and data pipelines in Node.
Streams & Workers
🌊 Stream Types

Readable — source of data (fs.createReadStream, HTTP req). Writable — destination (fs.createWriteStream, HTTP res). Duplex — both (TCP socket). Transform — modify in transit (zlib, crypto). Chain with .pipe() or stream.pipeline() (handles errors automatically).

⚙ Worker Threads

For CPU-intensive work (image processing, heavy computation) that would block the event loop. Workers run in isolated V8 contexts with their own event loop. Communicate via postMessage / SharedArrayBuffer. Don't use for I/O — that's already async. Pool workers with piscina for production.

🚀
Clustering, PM2 & Performance
Node is single-threaded — to utilise all CPU cores you must cluster. PM2 manages processes in production.
🔀 Cluster Module

cluster.fork() spawns one worker per CPU core. Master distributes connections using round-robin (Linux) or OS-handled (Windows). Workers share the same port. If a worker crashes, master restarts it.

os.cpus().lengthIPC messaging
🛠 PM2 Process Manager

pm2 start app.js --instances max starts a cluster automatically. Provides zero-downtime reloads (pm2 reload), log aggregation, CPU/memory monitoring, auto-restart on crash, and startup scripts.

pm2 reloadecosystem.config.js
📊 Profiling Node

Built-in: --prof flag generates V8 profiler output. node --inspect for Chrome DevTools debugging. clinic.js (flame, bubbleprof, heapProfiler) for production profiling. Track: event loop lag (toobusy-js), heap usage (process.memoryUsage), GC pauses.

clinic.js--prof

Express.js — Middleware Architecture
Minimalist, unopinionated web framework. Everything in Express flows through a middleware chain — understanding this is the key to mastering it.
Express Middleware Pipeline
🔗 Middleware Chain

Each middleware receives (req, res, next). Call next() to pass to the next handler, next(err) to jump to error handler. Order matters — middleware runs top-to-bottom in registration order. Application-level vs router-level vs built-in vs third-party.

🗺 Router

express.Router() creates a mini-application with its own middleware stack. Enables feature-based routing: userRouter.js, productRouter.js mounted at /api/users, /api/products. Use router.param() for id validation reuse across routes.

⚠ Error Handling

Error middleware has 4 args: (err, req, res, next). Must be registered LAST. Use a centralised error class hierarchy. async route handlers need try/catch or express-async-errors wrapper to propagate to error middleware.

MongoDB — Document Model & Architecture
Flexible document database storing BSON data. Schema-less by design, but best practice is to enforce schemas via Mongoose or JSON Schema validation.
MongoDB Architecture
📄 Data Modelling

Embed related data when it's accessed together and doesn't exceed 16MB. Reference (normalise) when data is large, frequently updated independently, or shared across documents. Rule of thumb: embed for one-to-few, reference for one-to-many/many-to-many.

Embed$refMongoose
🔍 Indexing Strategy

Single field for equality queries. Compound index for multi-field queries (follow ESR rule: Equality, Sort, Range). Text index for full-text search. TTL index auto-deletes documents after expiry. Use .explain("executionStats") to verify index usage.

explain()ESR Rule
🔄 Replica Sets & Sharding

Replica Set: 1 primary + N secondaries. Writes go to primary, replicated to secondaries. Automatic failover (primary election in ~10s). Sharding: horizontal scaling — data split across shards by shard key. Choose shard key carefully to avoid hot spots.

Replica SetSharding

Aggregation Pipeline & Mongoose
MongoDB's aggregation framework transforms and analyses data through a pipeline of stages — the equivalent of SQL GROUP BY, JOIN, and subqueries.
🔗 Aggregation Stages
$match — filter documents (use early, leverages indexes)
$lookup — left outer join another collection
$group — group by field, compute $sum/$avg/$count
$project — include/exclude/reshape fields
$sort / $limit / $skip — pagination
$unwind — flatten array fields
🛠 Mongoose Patterns

Define schemas with types, validators, defaults, and virtuals. Middleware (pre/post hooks) on save, validate, remove. Populate for reference resolution. Lean queries (.lean()) for read-only — returns plain objects, 2–5× faster than full Mongoose documents.

Transactions (v4.0+)

Use sessions for multi-document ACID transactions. session.startTransaction() → operations → session.commitTransaction(). Requires replica set. Adds latency — use only when truly needed for data consistency.

PostgreSQL — Relational Power
The world's most advanced open-source relational database. ACID compliant, supports JSON, full-text search, window functions, CTEs and geospatial queries.
PostgreSQL Architecture
🔍 Query Planner

EXPLAIN ANALYZE reveals the execution plan. Key terms: Seq Scan (full table, no index), Index Scan (b-tree lookup), Index Only Scan (covers all columns needed). Cost = startup + per-row. Use VACUUM ANALYZE to keep statistics fresh for planner accuracy.

EXPLAIN ANALYZEVACUUM
📊 Index Types

B-Tree (default) — equality and range queries, ORDER BY. GIN — full-text search, JSONB, arrays (@> operator). GiST — geometric, network types, proximity. BRIN — very large tables with natural ordering (timestamps). Partial indexes for sparse filtered queries.

B-TreeGINBRIN
🔐 ACID & MVCC

MVCC (Multi-Version Concurrency Control): readers never block writers. Each transaction sees a snapshot. Isolation levels: Read Committed (default), Repeatable Read, Serializable. Use FOR UPDATE for pessimistic locking; optimistic locking via version columns.

MVCCFOR UPDATE

Advanced Features & Node.js Integration
Window functions, CTEs, JSONB, partitioning, and connecting from Node with pg/Prisma/Drizzle.
Node.js ↔ PostgreSQL
🪟 Window Functions

Compute over a set of rows related to current row without collapsing them. ROW_NUMBER() OVER(PARTITION BY dept ORDER BY salary) ranks within groups. LEAD/LAG access adjacent rows. Running totals: SUM(sales) OVER(ORDER BY date ROWS UNBOUNDED PRECEDING).

🧱 Partitioning

Range partitioning: split large tables by date (logs, events). List partitioning: by region/category. Hash partitioning: distribute evenly. Child tables inherit schema and constraints. Partition pruning: queries only scan relevant partitions. Dramatically improves performance on huge tables.

🔌 Node.js Clients

pg (node-postgres): low-level, full control. Pool with pg.Pool — default max 10 connections. Prisma: type-safe ORM, migrations, schema-first. Drizzle: SQL-like syntax, fastest growing, zero-runtime overhead. Knex: query builder, good for complex dynamic queries.

Docker — Containers & Images
Docker packages an application and its dependencies into a lightweight, portable container that runs identically on any machine — dev, staging, or production.
Docker Architecture
📦 Image Layers

Images are built in read-only layers stacked on a base image. Each Dockerfile instruction (RUN, COPY, ADD) creates a new layer. Layers are cached — if a layer hasn't changed, Docker reuses it, making rebuilds fast. Only changed layers are pushed/pulled from a registry.

Union FSLayer Cache
⚙ Dockerfile Best Practices

Use multi-stage builds to keep final images small. Put rarely-changing layers first (base OS, dependencies) and frequently-changing layers last (app code) to maximise cache hits. Use .dockerignore to exclude node_modules. Prefer COPY over ADD. Run as non-root user.

Multi-stage.dockerignore
🔗 Docker Compose

Defines multi-container applications in a single docker-compose.yml. Services, networks, volumes, and environment variables declared declaratively. docker compose up -d starts the whole stack. Ideal for local dev — mirrors production topology with one command.

compose uphealthcheck
🌐
Networking, Volumes & Registry
Containers are isolated by default — networking and volumes connect them to each other and to persistent storage.
🌐 Container Networking

bridge (default): containers on the same bridge can reach each other by name. host: container shares host network stack (no isolation). overlay: multi-host networking for Swarm/K8s. In Compose, each service is DNS-resolvable by its service name — postgres:5432 just works.

💾 Volumes & Bind Mounts

Named volumes managed by Docker, survive container removal, ideal for databases. Bind mounts map a host path into the container — great for dev hot-reload. tmpfs mounts stay in memory only. Always use volumes for stateful services in production.

🏛 Registry & CI Integration

Push built images to Docker Hub, GitHub Container Registry (ghcr.io), or AWS ECR. Tag with semantic versions and latest. In CI: docker build → docker push → deploy. Use image digest pinning in production to prevent supply-chain attacks via mutable tags.

Apache Kafka — Distributed Event Streaming
Kafka is a high-throughput, fault-tolerant distributed log. Producers publish events to topics; consumers read them independently at their own pace — enabling decoupled, real-time data pipelines.
Kafka Architecture
📦 Topics & Partitions

A topic is a named log. Topics are split into partitions — each an ordered, immutable sequence of records. Partitions enable parallelism: more partitions = more consumers. A partition key routes related events to the same partition, preserving order for a given entity (e.g. all events for user-id X).

retentioncompaction
🔁 Consumer Groups

A consumer group is a set of consumers that collectively read a topic. Each partition is assigned to exactly one consumer in the group — enabling parallel processing. If a consumer fails, Kafka rebalances partitions across remaining members. Different groups can read the same topic independently (fan-out pattern).

group-idoffset commit
🛡 Durability & Replication

Each partition has a configurable replication factor (typically 3). One broker is the leader; others are followers. Producers write to the leader; followers replicate. acks=all ensures writes are durable across all in-sync replicas. Zookeeper (or KRaft in modern Kafka) manages broker metadata and leader election.

acks=allKRaft

Kafka Streams, Connect & Use Cases
The Kafka ecosystem extends beyond pub/sub into real-time stream processing and data integration.
⚡ Kafka Streams

A lightweight Java/Scala library for building real-time stream processing apps. Reads from input topics, applies transformations (filter, map, join, aggregate, windowing), and writes to output topics. No separate cluster — runs in your app. Stateful operations use local RocksDB stores backed by Kafka changelog topics.

🔌 Kafka Connect

Framework for streaming data between Kafka and external systems — databases, S3, Elasticsearch — without writing code. Source connectors ingest data into Kafka (e.g. Debezium for CDC from PostgreSQL). Sink connectors write Kafka data to destinations. Hundreds of connectors available on Confluent Hub.
