class ErrorBoundary extends Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }
  static getDerivedStateFromError(err) {
    return { hasError: true };
  }
  componentDidCatch(err, info) {
    logToService(err, info);
  }
  render() {
    if (this.state.hasError)
      return <h2>Something went wrong.</h2>;
    return this.props.children;
  }
}
// Wrap any component tree
function App() {
  return (

      <UserProfile />
    </ErrorBoundary>
  );
}

Process large data without loading it fully into memory. Streams are the backbone of HTTP, file I/O and data pipelines in Node.

🌊 Stream Types

Readable — source of data (fs.createReadStream, HTTP req). Writable — destination (fs.createWriteStream, HTTP res). Duplex — both (TCP socket). Transform — modify in transit (zlib, crypto). Chain with .pipe() or stream.pipeline() (handles errors automatically).

Named volumes managed by Docker, survive container removal, ideal for databases. Bind mounts map a host path into the container — great for dev hot-reload. tmpfs mounts stay in memory only. Always use volumes for stateful services in production.

Apache Kafka — Distributed Event Streaming
Kafka is a high-throughput, fault-tolerant distributed log. Producers publish events to topics; consumers read them independently at their own pace — enabling decoupled, real-time data pipelines.
Kafka Architecture
📦 Topics & Partitions

A topic is a named log. Topics are split into partitions — each an ordered, immutable sequence of records. Partitions enable parallelism: more partitions = more consumers. A partition key routes related events to the same partition, preserving order for a given entity (e.g. all events for user-id X).

retentioncompaction
🔁 Consumer Groups

A consumer group is a set of consumers that collectively read a topic. Each partition is assigned to exactly one consumer in the group — enabling parallel processing. If a consumer fails, Kafka rebalances partitions across remaining members. Different groups can read the same topic independently (fan-out pattern).

group-idoffset commit
🛡 Durability & Replication

Each partition has a configurable replication factor (typically 3). One broker is the leader; others are followers. Producers write to the leader; followers replicate. acks=all ensures writes are durable across all in-sync replicas. Zookeeper (or KRaft in modern Kafka) manages broker metadata and leader election.

acks=allKRaft

TDD vs BDD vs ATDD — Key Differences
Three test-driven development approaches — each answering a different question: Does it work? (TDD) · Does it behave correctly? (BDD) · Does it meet acceptance criteria? (ATDD)
🔴 TDD — Test Driven Development
Who writes tests? Developers. Tests are written in the same language as the code (Jest, JUnit, pytest).
Focus: Individual functions, classes, units of code — does each unit work correctly in isolation?
The Red → Green → Refactor Cycle:
🔴 RED — Write a failing test first
🟢 GREEN — Write minimum code to pass
🔵 REFACTOR — Clean up, keep tests green
// 1. Write failing test
it('adds 2 + 2', () => {
  expect(add(2,2)).toBe(4); // FAILS
});
// 2. Implement just enough
const add = (a,b) => a+b;
✅ Best for: Unit tests, API logic, algorithms, libraries
🟢 BDD — Behaviour Driven Development
Who writes tests? Developers + QA + Business Analysts, collaboratively. Uses plain English (Gherkin syntax).
Focus: Feature behaviour from the user's perspective — does the system behave as expected in each scenario?
Given / When / Then Structure:
Feature: Login

  Scenario: Valid credentials
    Given I am on the login page
    When I enter valid credentials
    Then I should see the dashboard

  Scenario: Invalid password
    Given I am on the login page
    When I enter wrong password
    Then I see "Invalid credentials"
CucumberJasmineBehave (Python)SpecFlow (.NET)
✅ Best for: Feature specs, integration tests, shared understanding
🔵 ATDD — Acceptance Test Driven Dev
Who writes tests? The whole team: Business + Dev + QA together, before development starts.
Focus: Meeting the customer's acceptance criteria — does the system satisfy the business requirement end-to-end?
ATDD Process:
1. Discuss — Team defines acceptance criteria together
2. Distil — Convert criteria into automated tests
3. Develop — Write code to make acceptance tests pass
4. Demo — Stakeholder verifies and accepts
FitNesseRobot FrameworkCucumber
✅ Best for: User story validation, full-system E2E, stakeholder sign-off
